## 1. Что это за продукт

Учёт личных и семейных финансов: операции, категории, лимиты, цели, правила счетов,
доходность вкладов, инвестиции, долги, обязательные платежи, календарь событий, переводы между счетами, импорт чеков (OCR),
экспорт профиля в JSON, автообновление по кнопке. Разворачивается в Docker на Synology / Xpenology.

Технически: ASP.NET Core 8 + EF Core + SQLite + JWT, SPA на React 18 / TypeScript / Vite.
Один процесс отдаёт и API, и статику. База — один файл SQLite (`data/app.db` в dev,
том `schitayka-data` в Docker).

### Закрыто в текущей итерации (бэклог B1–B21, B27/N2 и мастер-профиль)

- **B9.** `POST /api/auth/change-password`: PBKDF2, минимальная длина 8, проверка текущего пароля; после смены увеличивается `User.PasswordVersion` и старые JWT отклоняются (`JwtBearerEvents.OnTokenValidated`). Форма — в «Настройках → Профиль».
- **B10.** Таблица `AuditLogs` + `AuditService` (только метаданные: файл, размер, результат; без паролей/текста чеков). Экспорт профиля, импорт чека/текста и смена пароля пишут журнал; просмотр — `GET /api/audit` и карточка «Журнал безопасности».
- **B11.** Перед миграцией/пересозданием/исправлением схемы делается консистентная копия через `VACUUM INTO` в `<папка БД>/backups/app.db.pre-migrate-*.db`. Хранятся последние 10 копий и не старше 30 дней; неудачный бэкап не блокирует запуск, но пишет предупреждение.
- **B12.** `dialogs.tsx` — единые `confirm/alert/prompt` вместо нативных; все обращения заменены, включая формы долгов/платежей/календаря.
- **B17.** JWT хранится в `sessionStorage` (`token.ts`) с памятным фолбэком; внешние Google Fonts удалены, используется системный стек шрифтов.
- **B19.** Политика знакового остатка: дебет со знаком минус = перерасход, кредитка со знаком минус = переплата. `Math.Max(0, …)` убран из ядра расчёта; в интерфейсе показываются подписи «перерасход»/«переплата». Лимит доступных средств в `TransferService` остаётся защитой от перевода в минус.
- **B20.** Для исторических пар `IsTransfer` без записи `Transfers` удаление одной половины однозначно находит вторую (сумма + дата + комментарий + противоположный тип), создаёт запись `Transfer` и отменяет перевод целиком; при нескольких кандидатах возвращается ошибка. Редактирование любой стороны перевода запрещено.
- **B1.** `POST /api/import/receipt/qr` — локальный разбор строки ФНС (`t/s/fn/i/fp/n`); во frontend вставка строки, QR из файла и камера через `jsqr`. Запрос к ФНС и новый base64-формат не реализованы.
- **B2.** `ILocalOcrProvider`/`IRemoteOcrProvider`: tesseract по умолчанию, OpenAI-совместимый vision включается только `Ocr:Provider=openai` + ключ; при любом сбое — fallback на локальный OCR. Изображения не отправляются без явной настройки.
- **B3.** Позиции чека (`ReceiptItem`) с чекбоксами; выбранные позиции сохраняются отдельными операциями, сумма сверяется с итогом чека (допуск 1 ₽).
- **B4.** `GET /api/export/profile?from=&to=&anonymize=&take=`: фильтр на уровне SQL, обезличивание, `schemaVersion=2` и `exportParams`, аудит без персональных значений. По умолчанию — полный экспорт как раньше.
- **B5.** `BudgetSummaryService` инкапсулирует расчёт сводки и рекомендаций; `BudgetController` — тонкая обёртка, JSON-контракт совместим.
- **B6.** Тема хранится в `User.Theme`, синхронизируется через `/api/settings/appearance`; серверное значение побеждает при логине, `localStorage` — офлайн-кэш.
- **B13.** Ретроактивное применение правил вынесено в `AccountRulesService.ApplyToExistingAsync`; UI — кнопка с подтверждением, фильтры по датам и опция перезаписи. Правила теперь действуют и на операции «за члена семьи».
- **B27/N2.** Канонический макет — гибрид: светлая «стеклянная» карточка/брендовые цвета, тёмный акцент вклада с жёлтым бейджем и кольцо доходности.
- **B8.** Workflow `.github/workflows/docker-ghcr.yml` публикует образ `ghcr.io/nikolayudin/schitayka` при релизе/теге `v*`; `docker-compose.image.yml` использует готовый образ вместо сборки на NAS.
- **B14.** Удалена legacy-«гармонизация» схемы из `Program.cs`: остались только EF-миграции, baseline для старых БД и авто-бэкап B11. Проверки и бэкап теперь опираются на фактический путь из строки подключения.
- **B16.** npm-сборка больше не запускается при `dotnet build`/`publish`; включается явным `-p:BuildFrontend=true`. CI и релизный скрипт собирают фронтенд отдельно, готовый `backend/wwwroot` хранится в репозитории.
- **B15.** N+1 устранён: владельцы, банки, имена счетов и стартовые балансы загружаются пакетно; правила матчатся компактными выборками. Контракт ответов не изменён, число SQL-команд не растёт при увеличении числа счетов/правил.
- **B18.** `WebApplicationFactory<Program>` с изолированной SQLite-БД на тест: 6 HTTP-сценариев — первичная настройка, логин и `/me`, инвалидация JWT после смены пароля, роли администратора, тема, экспорт с параметрами.
- **B21.** Единая шкала прогресса самообновления 0..100, монотонные шаги, корректные 100 % и `FinishedAt`, сброс при ошибке, общий мьютекс для состояния и лога; в UI показывается название шага и честная полоса прогресса.
- **Вместо B7.** В БД создаётся мастер-профиль (служебный пользователь без пароля). `POST /api/setup/admin` доступен до первого администратора и превращает мастер-профиль в первого пользователя с ролью `Master`. ## 8. Договорённости и решения

- **Аутентификация:** публичная регистрация отключена; новые записи создаёт администратор семьи. При первом запуске мастер-профиль в БД создаёт первого пользователя с ролью `Master` (`/api/setup/admin`). Вход через Yandex ID не реализуется по решению пользователя.
- **Баланс** считается в `AccountBalanceService`; переводы — `Transfer` + две операции с `IsTransfer=true` (флаг выставляет сервер).
- **Семейные переводы (N3):** перевод принадлежит владельцу счёта-отправителя, половины распределяются по владельцам счетов; видимость/отмена — в рамках семьи (`FamilyAccess`).
- **Охват дашборда (N4):** `me/family/ids` влияет на агрегаты сводки; лимиты/цели/уведомления/резервы — личные.
- **Банки:** справочник (системные + свои), привязка к счетам; системные банки не удаляются; свои неиспользуемые можно удалить (в т.ч. массово), неиспользуемые можно скрыть в списке настроек.
- **Долги (Задача 2):** учитываются отдельно и не входят в доходы/расходы бюджета; остаток пересчитывается из основной суммы и истории событий; операция по счёту создаётся только по галочке при возврате/оплате процентов (категория «Долги», кэшбэк по ней не начисляется).
- **Обязательные платежи (Задача 3):** сам платёж — план и в бюджет не входит; операция создаётся по галочке при оплате и является обычным расходом (в т.ч. с кэшбэком); дата следующего платежа сдвигается на один период от даты по графику.
- **Связь долгов и платежей (Задача 4):** `Obligation.DebtId` указывает только на долг «я должен»; по галочке при оплате создаётся событие `Repayment` и уменьшается остаток, но вторая операция по счёту не создаётся. Событие живёт вместе с фактом оплаты: удаление факта/платежа возвращает остаток, отдельное удаление события из истории долга запрещено. Виджеты включаются независимо.
- **Календарь (Задача 5):** объединяет даты обязательных платежей, сроков долгов, окончания вкладов, неоплаченных начислений процентов и пользовательских событий; только отображение и напоминания-признаки, никакой агрегации сумм в бюджете. Виджет «Ближайшие события» имеет собственный переключатель.
- **Категории семьи (после 0.3.6):** у категории есть `FamilyCode`; все члены семьи видят и редактируют один список. При вступлении в семью одноимённые категории сливаются, ссылки в операциях, лимитах, обязательствах и правилах перенаправляются на каноническую запись. Лимиты остаются личными.
- **Охват «я / семья» (после 0.3.6):** `sk_scope` общий для дашборда, долгов, платежей и календаря; разбор параметра вынесен в `FamilyAccess.ResolveScopeAsync`. В режиме семьи показываются и редактируются записи всех членов семьи; операции по семейному счёту записываются его владельцу.
- **Миграции:** EF Core; секреты не хранятся в репозитории/архивах.
- **Релизы:** тег `vX.Y.Z`, ассеты docker.zip, app.zip, sha256 (см. процесс в `PLAN.md` / `deploy/xpenology/release/PACKAGING.md`).
