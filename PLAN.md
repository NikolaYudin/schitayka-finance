## Принципы

1. **Данные пользователя неприкосновенны.** Никаких `EnsureDeleted()` в рабочем режиме, экспорт/импорт — только по явному действию.
2. **Сначала фундамент, потом фичи.** Новые сущности (правила, настройки, импорт) требуют нормальных миграций, а не ручной «гармонизации» схемы в `Program.cs`.
3. **Приватность по умолчанию.** Финансовые данные чувствительны: изображения чеков не храним, наружу отправляем только по согласию, экспорт не содержит секретов.
4. **Обратная совместимость.** Старые `app.db` должны открываться без потери данных.
5. **Каждая фича = API + UI + тесты + документация.**

## Задача 0. Правила для счетов

> **Статус:** ✅ реализовано — движок правил, API, миграция, уведомления, займы из резерва, UI, тосты, тесты.

«Правила счетов» — это **три независимых типа правил**, объединённых одним разделом UI и общим API. Пользователь может включать их по отдельности.

| Код | Тип | Суть |
|---|---|---|
| 0.1 | **Автоподстановка** | По признакам операции автоматически выбрать счёт и (опционально) категорию |
| 0.2 | **Неснижаемый остаток** | Минимум на счёте; при нарушении — уведомление |
| 0.3 | **Резерв на экстренные нужды** | Неприкосновенная сумма; если её тратят — это заём, а возврат контролируется напоминанием (без блокировки) |

### 0.1. Автоподстановка счёта и категории

Движок, который автоматически определяет **счёт** (и опционально **категорию**) для операции по её признакам. Примеры:

- «Если комментарий содержит "Пятёрочка" → счёт "Основная карта", категория "Продукты"».
- «Если категория = "Транспорт" → счёт "Наличные"».
- «Если сумма от 50 000 ₽ и тип = расход → счёт "Кредитная карта"».

### 0.2. Неснижаемый остаток + уведомления

- Для счёта задаётся **минимальный остаток** (например, «не опускаться ниже 10 000 ₽»).
- При каждом пересчёте баланса проверяется условие:
  - дебет/наличные/вклад: `balance < threshold`;
  - кредитная карта: `balance (долг) > threshold` — трактуется как «не превышать долг / использовать не более X».
- Если условие нарушено — создаётся **уведомление** (MVP: внутри приложения). Когда баланс восстановился — уведомление автоматически закрывается.
- Дедупликация: одно активное уведомление на пару «счёт + правило»; повторно не спамим, пока проблема не устранена. Опционально — повтор раз в сутки, если ситуация ухудшилась.
- Каналы: MVP — **всплывающее окно (toast)** при срабатывании + блок в «Обзоре» и на карточке счёта. Счётчик/центр уведомлений и внешние каналы (email, Telegram) — позже (P2, отдельный `NotificationChannel`).

### 0.3. Резерв на экстренные нужды (с напоминанием о возврате)

- Пользователь сам решает, **где задать резерв**: на конкретном счёте или общий на все некредитные счета (`AccountRule.AccountId = null`). Можно завести несколько правил под разные сценарии.
- Резерв — сумма, которую пользователь считает неприкосновенной («подушка безопасности»).
- Расчёт свободного резерва:
  - резерв на счёте: `max(0, min(balance, threshold) − невозвращённые займы по этому счёту)`;
  - общий резерв: `max(0, min(сумма балансов некредитных счетов, threshold) − все невозвращённые займы)`.
- Если пользователь тратит деньги, из-за которых баланс опускается ниже резерва, приложение предлагает оформить это как **заём из резерва**: сумма, дата, срок возврата (по умолчанию из правила, например 30 дней), комментарий.
- Заём отображается в «Обзоре» и на карточке счёта: «Из резерва взято 5 000 ₽, вернуть до 09.12.2026».
- Возврат — **только напоминание**: приложение показывает срок, подсвечивает просрочку и предлагает кнопку «Вернул» (она закрывает заём), но никогда не блокирует траты и не списывает деньги автоматически. Возврат также можно привязать к доходной операции.
- Просроченный заём → всплывающее окно уровня `danger` + блок в «Обзоре» с рекомендацией «вернуть в резерв».
- Никаких блокировок и «мягких ограничений» — только информирование.

### Общая модель данных

Новые сущности в `backend/Data/AppDbContext.cs`:

```csharp
public enum AccountRuleKind { AutoAssign = 0, MinBalance = 1, EmergencyReserve = 2 }

public class AccountRule
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public User User { get; set; } = null!;
    public string Name { get; set; } = "";
    public AccountRuleKind Kind { get; set; }
    public bool IsEnabled { get; set; } = true;
    public int Priority { get; set; } = 100;       // меньше = раньше (для AutoAssign)

    // Целевой счёт: для AutoAssign и MinBalance — обязателен;
    // для EmergencyReserve — null означает «общий резерв по всем некредитным счетам».
    public int? AccountId { get; set; }
    public Account? Account { get; set; }

    // --- AutoAssign ---
    public TxType? TxType { get; set; }
    public int? MatchCategoryId { get; set; }
    public string? CommentContains { get; set; }
    public decimal? AmountMin { get; set; }
    public decimal? AmountMax { get; set; }
    public int? SetCategoryId { get; set; }        // опционально: автокатегория

    // --- MinBalance / EmergencyReserve ---
    public decimal? Threshold { get; set; }        // минимальный остаток / размер резерва
    public int? DefaultReturnDays { get; set; }    // срок возврата займа из резерва
    public bool NotifyInApp { get; set; } = true;

    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
}

public class AccountAlert
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public int? AccountId { get; set; }             // null — уведомление по общему резерву
    public int? RuleId { get; set; }
    public string Kind { get; set; } = "";          // MinBalance | ReserveBroken | ReserveOverdue
    public string Level { get; set; } = "warn";     // warn | danger
    public string Message { get; set; } = "";
    public decimal BalanceSnapshot { get; set; }
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public DateTime? ResolvedAt { get; set; }
    public DateTime? DismissedAt { get; set; }
}

public class ReserveLoan
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public int AccountId { get; set; }
    public int? RuleId { get; set; }
    public decimal Amount { get; set; }
    public DateTime TakenAt { get; set; } = DateTime.UtcNow;
    public DateTime DueDate { get; set; }
    public DateTime? ReturnedAt { get; set; }
    public int? TransactionId { get; set; }         // операция, из-за которой взяли
    public string Comment { get; set; } = "";
}
```

- FK на `Account` — `Cascade`; на категорию — `SetNull`; индексы `(UserId, Priority)`, `(UserId, AccountId, ResolvedAt)`, `(UserId, ReturnedAt, DueDate)`.
- Миграция EF Core (см. A6).

### Движок и интеграция

`backend/Services/AccountRulesService.cs`:


Точки вызова:
- `TransactionsController.Create/Update/Delete` — после `RecalcAccounts` (баланс изменился → проверяем минимум/резерв).
- `AccountsController.Create/Update/Adjust/Cashback/Delete` — после пересчёта.
- `GET /api/accounts` и `/api/budget/summary` — `EvaluateAllAsync`, чтобы уведомления были свежими даже без новых операций (например, наступил срок возврата).
- Будущий импорт из изображения (Задача 2) — `MatchAssignmentAsync` для предзаполнения.

Особенности:
- Условия AutoAssign объединяются через **И**; пустое условие игнорируется; регистронезависимый `Contains` для русского считаем в памяти (`ToLowerInvariant()`).
- Для `EmergencyReserve` с `AccountId = null` порог сравнивается с суммой балансов некредитных счетов. Заём при этом всё равно привязывается к конкретному счёту, с которого реально ушли деньги.
- Уведомления не дублируются: ищем активное (`ResolvedAt == null && DismissedAt == null`) по `(RuleId, AccountId, Kind)`; если условие ушло — ставим `ResolvedAt`.
- Bulk-apply: пакетами по 500, в транзакции, с отчётом; не трогаем операции с уже заданным счётом (если не передан `overwrite=true`).
- Производительность: правила читаются один раз за запрос; кэш `IMemoryCache` с инвалидацией при изменении правил.

- Юнит: комбинации условий и приоритеты AutoAssign; границы threshold; дедупликация/автозакрытие уведомлений; расчёт свободного резерва; просрочка займа.
- Интеграционные: create/update/delete операции триггерят проверку; bulk-apply не задевает чужие данные; займы и уведомления изолированы по `UserId`; архивные счета не используются.

### Критерии готовности

- 0.1: правило создаётся/отключается/удаляется и применяется к новым операциям; dry-run показывает точное число затронутых операций и не меняет данные.

- 0.3: резерв можно задать на конкретном счёте или общим на все некредитные счета; можно взять и вернуть заём; свободный резерв считается корректно; просрочка видна в «Обзоре»; возврат — только напоминание, траты не блокируются.
- Уведомления работают в приложении; email/push — вне MVP.
- Чужие счета/категории и архивные счета недоступны.

## Задача 1. Дневная / ночная тема

> **Статус:** ✅ реализовано — CSS-переменные, тёмная палитра, режимы `light / dark / system`, переключатель в шапке и настройках, защита от FOUC.

### Подход

В `index.css` уже есть CSS-переменные, но часть цветов захардкожена (`#fff`, `#edf2f7`, `#fbfdff`, `#718096`, тени). План:

1. **Вынести все цвета в переменные** (`frontend/src/index.css`):
   `--bg`, `--card-bg`, `--surface`, `--surface-alt`, `--text`, `--text-muted`, `--border`, `--input-bg`, `--nav-bg`, `--shadow`, `--overlay`, `--primary-soft` и т.д.
2. **Два набора значений**:
   ```css
   :root { /* светлая */ --bg:#f7fafc; --card-bg:#fff; --text:#2d3748; ... }
   [data-theme="dark"] { --bg:#0f172a; --card-bg:#1e293b; --surface-alt:#334155;
                          --text:#e2e8f0; --text-muted:#94a3b8; --border:#334155;
                          --input-bg:#0f172a; --nav-bg:#1e293b; ... }
   ```
   Подобрать контраст ≥ 4.5:1 для текста, проверить бейджи, рекомендации, прогресс-бары и inline-цвета категорий/счетов (для тёмного фона добавить светлую обводку или осветлять цвета на 10–15%).
3. **Режимы:** `light | dark | system`, хранение в `localStorage('sk_theme')`.
   - Хук `frontend/src/theme.ts`: применяет `document.documentElement.dataset.theme`, слушает `matchMedia('(prefers-color-scheme: dark)')` для режима `system`.
   - Обновлять `<meta name="theme-color">` под выбранную тему.
4. **Без «вспышки» белого** (FOUC): маленький inline-скрипт в `frontend/index.html` до загрузки CSS — читает `localStorage` и ставит `data-theme` на `<html>`. Vite сохраняет этот скрипт в сборке.
5. **UI переключения:**
   - иконка ☀️/🌙 в `topbar` (быстрое переключение светлая↔тёмная);
   - в `Settings` — выбор «Светлая / Тёмная / Системная».
6. **Опционально (P2):** хранить выбор на сервере (`User.Theme`) и синхронизировать между устройствами (`PUT /api/profile/preferences`). Тогда тема не слетает при очистке браузера.

### Тесты / проверка

- Ручной чек-лист всех экранов в обеих темах (вход, обзор, счета, журнал, цели, лимиты, настройки, модалка, семья).
- Контраст текста и интерактивных элементов; фокус-обводки.
- Нет FOUC при холодной загрузке и при `system` + смене темы ОС.

**Оценка:** 1–1,5 дня (+0,5 дня на серверную синхронизацию).

## Задача 2. Добавление операций из изображения (чек/фото)

> **Статус:** ✅ реализовано (MVP, путь B — OCR). `POST /api/import/receipt` (`[Authorize]`, ≤ 10 МБ, JPG/PNG/WebP/BMP/TIFF) → локальный `tesseract` (`rus+eng`, таймаут 30 с, настраивается через `Ocr:*`) → `ReceiptParser` извлекает итог, дату, магазин и подсказывает категорию/счёт. Резервный путь — `POST /api/import/receipt/text` (ручная вставка текста), работает и без tesseract. Изображение пишется в temp-файл и удаляется в `finally`; текст не логируется. UI: загрузка фото + форма предпросмотра с правкой перед сохранением.
> **Не реализовано (оставлено на будущее):** путь A — декодирование QR ФНС и запрос состава чека у провайдера; облачные OCR-провайдеры (Yandex/Google Vision); разбивка чека на позиции.

### Стратегия: два пути, один API

**Путь A — QR-код чека (приоритет для РФ).** На бумажных чеках ФНС есть QR с параметрами `t, s, fn, i, fp, n`. Он даёт точные данные без OCR. Декодировать QR (клиент — `jsQR`, или сервер — `ZXing.Net`), затем получить состав чека через провайдера (ФНС/«Проверка чеков»). Точность максимальная, но нужен внешний запрос и согласие пользователя.

**Путь B — OCR.** Если QR нет/не читается: распознать текст и вытащить эвристиками итог, дату, магазин.
- Локально: `Tesseract` (rus+eng), без передачи данных наружу, но точность на фото ниже и нужны языковые данные (~50 МБ).
- Облако: Yandex Vision OCR (лучше для русских чеков), Google Vision, Azure Document Intelligence. Требует ключей и оплаты.
- Рекомендация: MVP = QR + ручное подтверждение; OCR — второй шаг за абстракцией провайдера.

### Backend

`backend/Controllers/ImportController.cs`:

- `POST /api/import/receipt` — `multipart/form-data`, `[Authorize]`, лимит 10 МБ, разрешённые типы `image/jpeg|png|webp|heic`, pdf — позже. Rate limit.
- Конвейер:
  1. валидация файла (размер, MIME по содержимому, не доверять расширению);
  2. попытка декодировать QR → при успехе запрос к провайдеру чеков;
  3. иначе OCR (провайдер из конфига);
  4. нормализация текста + парсер;
  5. ответ `ReceiptParseResult`:
     ```json
     {
       "source": "qr|ocr",
       "confidence": 0.87,
       "total": 1234.50,
       "date": "2026-11-08",
       "merchant": "Пятёрочка",
       "items": [{ "name": "Молоко", "qty": 1, "sum": 89.90 }],
       "suggestedCategoryId": 12,
       "suggestedAccountId": 3,
       "rawText": "..."
     }
     ```
- **Ничего не сохраняем автоматически.** Файл — во временную папку/поток, удаляется в `finally`; текст не логируем.
- `backend/Services/ReceiptParser.cs` — регулярки для «ИТОГ/ИТОГО/К ОПЛАТЕ», даты `dd.MM.yyyy`, строк товаров; юнит-тесты на обезличенных образцах.
- `backend/Services/IOcrProvider.cs` + реализации `TesseractOcrProvider`, `YandexOcrProvider`, `NullOcrProvider`.
- Конфиг (env/user-secrets, не в git): `Ocr:Provider`, `Ocr:Yandex:ApiKey`, `Ocr:Yandex:FolderId`, `Ocr:MaxFileMb`.
- Безопасность: таймаут 20–30 с, ограничение параллельных запросов, очистка временных файлов, запрет на SSRF (не ходить по URL из изображения).

### Frontend

- Кнопка **«📷 Загрузить чек»** в `QuickTxModal` и/или в FAB-меню.
- `<input type="file" accept="image/*" capture="environment">` + drag&drop, превью.
- Прогресс распознавания → форма **предпросмотра**: итог, дата, магазин, категория (с учётом правил из Задачи 0), счёт; пользователь правит и жмёт «Сохранить».
- Опция «разбить на позиции» — P2 (создать несколько операций по товарам).
- Понятные ошибки: «QR не найден», «Не удалось распознать сумму», «Провайдер недоступен» + fallback на ручной ввод.

### Приватность и юридические аспекты

- Явный текст согласия: «Изображение будет отправлено в <провайдер> для распознавания» (для облака).
- Настройка «не отправлять наружу» (только локальный OCR/QR).
- Изображения не хранятся; в экспорт (Задача 3) они не попадают.

### Тесты

- Набор из 10–20 реальных обезличенных чеков: доля корректно извлечённого итога/даты (цель ≥ 90% для QR, ≥ 70% для OCR).
- Негативные: битый файл, гигантский файл, не-изображение, чек без QR.
- Проверка, что после запроса в temp не остаётся файлов.

### Критерии готовности

- Пользователь загружает фото, получает предзаполненную форму, подтверждает — создаётся операция.
- Ни одно изображение не сохраняется на диск после запроса.
- При недоступном OCR приложение не падает и предлагает ручной ввод.

**Оценка:** QR-путь — 1,5–2 дня; OCR + парсер — 3–5 дней; итого ~1 неделя.

## Задача 3. Экспорт полного профиля в JSON для ИИ-агента

> **Статус:** ✅ реализовано (MVP). `GET /api/export/profile` (`[Authorize]`, только собственные данные, без данных семьи) отдаёт файл `schitayka-profile-*.json` со `schemaVersion: 1`: `meta`, версия приложения (`application`), пользователь, сводка (текущий месяц и всё время, норма сбережений, кэшбэк), счета, категории, операции, лимиты с фактическим расходом, цели с расчётом «в месяц», правила счетов с остатком резерва, активные уведомления, невозвращённые займы из резерва, аналитика по месяцам и структура расходов. Пароли, JWT, `FamilyCode` и чужие данные не попадают. UI: «Настройки» → скачивание файла через `fetch` + `Blob`.
> **Отличия от плана:** нет параметров `from/to` и `anonymize` — экспортируется весь профиль целиком; `BudgetSummaryService` не выделен, сводка считается внутри контроллера (рефакторинг остаётся в бэклоге).

### API

`GET /api/export/profile?from=YYYY-MM-DD&to=YYYY-MM-DD&anonymize=false`

- `[Authorize]`, только свои данные, `Cache-Control: no-store`.
- Ответ: `application/json; charset=utf-8`, `Content-Disposition: attachment; filename="schitayka-profile-YYYYMMDD.json"`, потоковая сериализация (`JsonSerializer.SerializeAsync` в `Response.Body`).
- Лимиты: максимум диапазона (например, 5 лет) и количества операций; иначе 400 с понятной ошибкой.

### Схема (versioned)

```json
{
  "schemaVersion": 1,
  "generatedBy": "СчитайКа",
  "exportedAt": "2026-11-09T12:00:00Z",
  "currency": "RUB",
  "period": { "from": "2025-01-01", "to": "2026-11-09" },
  "user": { "id": 1, "name": "Демо", "email": "demo@...", "createdAt": "..." },
  "summary": {
    "monthIncome": 95000, "monthExpense": 42150, "balance": 52850,
    "totalBalance": 312000, "savingsRate": 55.6, "cashbackTotal": 1234
  },
  "accounts": [ { "id": 1, "name": "Основная карта", "type": "DebitCard",
                  "balance": 30000, "creditLimit": 0, "cashbackRate": 5 } ],
  "categories": [ { "id": 3, "name": "Продукты", "type": "Expense", "isSystem": true } ],
  "transactions": [ { "id": 10, "date": "2026-11-01", "type": "Expense",
                      "amount": 1234.5, "category": "Продукты",
                      "account": "Основная карта", "comment": "..." } ],
  "limits": [ { "category": "Продукты", "year": 2026, "month": 11, "limit": 20000, "spent": 12350 } ],
  "goals": [ { "name": "Отпуск", "targetAmount": 150000, "currentAmount": 4468.94,
               "deadline": "2027-04-01", "monthsLeft": 5, "perMonth": 29106 } ],
  "analytics": { "byMonth": [ { "year": 2026, "month": 10, "income": 95000, "expense": 42150 } ],
                 "expenseShare": [ { "category": "Продукты", "total": 12350, "sharePct": 29.3 } ] },
  "recommendations": [ { "level": "warn", "text": "..." } ],
  "meta": { "counts": { "transactions": 120, "accounts": 4, "goals": 2 } }
}
```

Правила:
- **Никогда** не экспортировать `PasswordHash`, `YandexId`, JWT, cookie.
- `anonymize=true` — заменить email/имена/комментарии псевдонимами (`user`, `account_1`, `tx_1`), сохранив суммы и даты (для анализа агентом этого достаточно).
- Единицы: суммы в рублях, даты ISO-8601, `type` — строки (`Income`/`Expense`), а не магические 0/1.
- В `meta.notes` — краткое описание полей, чтобы агенту не приходилось угадывать.
- В экспорт попадают и данные правил счетов (0.1–0.3) и активные уведомления — чтобы агент видел финансовые обязательства.

### Рефакторинг

Логику сводки из `BudgetController.Summary` вынести в `backend/Services/BudgetSummaryService.cs`, чтобы `/api/budget/summary` и экспорт считали одинаково (и чтобы исправление A3 автоматически попало в экспорт).

### Frontend

- `Settings` → карточка **«Экспорт для анализа»**: диапазон дат, чекбокс «обезличить», кнопка «Скачать JSON».
- Скачивание через `fetch` (нужен `Authorization`) → `Blob` → `URL.createObjectURL` + программный `<a download>`.
- Предупреждение о приватности и о том, что файл содержит финансовые данные.
- Показывать размер файла/количество операций до скачивания (опционально `HEAD`-эндпоинт или расчёт на клиенте).

### Тесты

- Схема соответствует версии (golden-file тест).
- В выводе нет запрещённых полей (проверка по списку).
- Фильтрация по датам корректна, чужие данные недоступны.
- Большой профиль (10k операций) не роняет сервер по памяти.

**Оценка:** 2 дня.

## Задача 4. Дистрибутив для Container Manager (zip-архив)

> **Статус:** ✅ каркас реализован — шаблоны compose, скрипты, README, упаковщик (`build-release.ps1` / `.sh`), архив собирается и проверяется. ✅ **Релиз 0.1.0 опубликован**: https://github.com/NikolaYudin/schitayka-finance/releases/tag/v0.1.0 (вложение `schitayka-0.1.0-docker.zip`, SHA256 `9D1CA4B…F628E28`).
> ⬜ осталось: прогон на реальном NAS и публикация готового образа (B8).
> **Версия:** 1.2.0.

### Сценарий пользователя

> «Скачал zip → распаковал в папку `docker` → Container Manager → Проект → Создать → путь `/docker/schitayka` → Готово».

Без git, без SSH, без правки путей в compose. Это главный критерий: **три шага и ни одного ручного исправления файлов**.

### Архитектура архива

```
schitayka-<версия>-docker.zip
└── schitayka/                      ← корень = папка проекта Container Manager
    ├── docker-compose.yml          ← context: ./app, внешние пути не нужны
    ├── docker-compose.image.yml    ← вариант без сборки (готовый GHCR-образ)
    ├── .env                        ← APP_PORT, JWT_KEY (сгенерирован), TZ, SEED_DEMO
    ├── .env.example                ← шаблон, если .env потерян
    ├── VERSION
    ├── MANIFEST.txt                ← версия, коммит, дата, состав
    ├── README.md                   ← инструкция: распаковка → .env → проект
    ├── app/                        ← контекст сборки Docker
    │   ├── Dockerfile
    │   ├── .dockerignore
    │   ├── VERSION
    │   ├── backend/                ← без bin/obj/wwwroot/app.db
    │   └── frontend/               ← без node_modules/dist
    └── scripts/
        ├── init-env.sh             ← создать .env + сгенерировать JWT_KEY
        ├── update.sh               ← пересобрать и перезапустить
        ├── backup.sh               ← копия тома schitayka-data
        └── restore.sh              ← восстановление из копии
```

Данные **не в архиве**: SQLite живёт в именованном томе `schitayka-data`, поэтому обновление кода и распаковка нового zip не затрагивают базу.

### Ключевые решения

| Решение | Почему так |
|---|---|
| `docker-compose.yml` в корне, `build.context: ./app` | Container Manager не умеет контекст сборки вне папки проекта. Текущий `deploy/xpenology` использует `../..` — мастер UI его не принимает, нужен весь репозиторий |
| Исходники в `app/`, Dockerfile без изменений | Dockerfile и так ждёт `backend/`, `frontend/`, `VERSION` в корне контекста — достаточно поменять контекст, а не Dockerfile |
| Именованный том `schitayka-data` | Bind-mount `./data` на Synology часто даёт `permission denied` для пользователя контейнера (uid 1654) из-за ACL; том переживает пересборку и обновление |
| Готовый `.env` с `JWT_KEY` в архиве | Убирает обязательный шаг «сгенерируй ключ на NAS». Публичные сборки — `-NoEnv`, ключ генерируется `scripts/init-env.sh` |
| Скрипты с LF и запуском через `sh` | Zip на Windows теряет бит `+x`, а CRLF ломает shebang на DSM. Поэтому `sh scripts/update.sh`, а упаковщик принудительно ставит LF |
| Архив без git | Обновление = замена папки `app/`; git на NAS не нужен |
| Два compose-файла | `docker-compose.yml` — сборка на NAS (по умолчанию), `docker-compose.image.yml` — готовый образ для слабых/ARM-моделей |
| `backend/wwwroot` не кладём в архив | SPA собирается внутри Dockerfile (Node-стадия); старые хешированные ассеты только раздувают контекст |
| `app.db` не кладём в архив | Локальная демо-база разработчика не должна попадать на NAS |

### Состав и ответственность

| Файл | Ответственность |
|---|---|
| `release/docker-compose.yml` | Проект CM: порт, `.env`, том, healthcheck, лимиты логов |
| `release/docker-compose.image.yml` | То же без `build`, `image: ghcr.io/...` |
| `release/.env.example` | Шаблон переменных с комментариями |
| `release/scripts/init-env.sh` | `.env` из шаблона + `openssl rand -base64 48` |
| `release/scripts/update.sh` | `compose up -d --build` (или `--no-build`) |
| `release/scripts/backup.sh` | Стоп → `docker cp` тома → `tar.gz` → старт (целостная копия SQLite/WAL) |
| `release/scripts/restore.sh` | Стоп → очистка тома → распаковка → `chown app:app` → старт |
| `release/README.md` | Инструкция внутри архива: 3 шага, бэкап, обновление, HTTPS, диагностика |
| `release/build-release.ps1` | Упаковщик для Windows: staging → LF → `.env` → MANIFEST → zip → проверка обязательных файлов |
| `release/build-release.sh` | То же для Linux/CI (`rsync`/`cp`, `zip` или python-фолбэк) |

### Инструкция по реализации

1. **Шаблоны compose** — `context: ./app`, `image: schitayka:latest`, `Jwt__Key: ${JWT_KEY:?...}`, том `schitayka-data`, healthcheck `/api/health`. Отдельный `docker-compose.image.yml` без `build`.
2. **Скрипты** — POSIX `sh`, без bash-измов (на DSM busybox), `set -eu`, определение `docker compose` / `docker-compose`, LF.
3. **README архива** — писать под сценарий «я не читал репозиторий»: что внутри, требования, 3 шага, проверка, первый вход, бэкап/восстановление, обновление, HTTPS, диагностика, удаление.
4. **Упаковщик** — параметры `-Version`, `-OutputDir`, `-RootName`, `-NoEnv`, `-Image`, `-KeepStage`; исключения по **полным путям** (не по именам: `data` регистронезависимо вырезает `backend/Data`); `.env` с ключом; `MANIFEST.txt`; `Compress-Archive`; проверка списка обязательных файлов внутри zip.
5. **Проверки перед публикацией** (все выполняются автоматически/полуавтоматически):
   - распаковать архив в чистую папку и `dotnet build backend/SchitayKa.Api.csproj` — 0 ошибок;
   - `bash -n` для всех `scripts/*.sh`, в файлах нет `CR`;
   - YAML парсится (`python -c "yaml.safe_load(...)"`);
   - в архиве есть `docker-compose.yml`, `.env`, `app/Dockerfile`, `backend/Data/AppDbContext.cs`, `frontend/package-lock.json`, `scripts/update.sh`;
   - в архиве **нет** `app.db`, `node_modules`, `bin`, `obj`, `wwwroot`.
6. **Документация репозитория** — раздел «Установка из zip» в `README.md` и `deploy/xpenology/README.md` со ссылкой на `deploy/xpenology/release/`.
7. **Выпуск** — поднять `VERSION`, собрать `build-release.ps1`, приложить zip к GitHub Release, указать SHA256 из вывода.

### Обновление у пользователя

1. Скачать новый zip → распаковать в `schitayka-new`.
2. Container Manager → проект → **Остановить**.
3. Заменить `app/`, `docker-compose.yml`, `scripts/`; **`.env` не трогать**.
4. **Сборка → Запуск** (или `sh scripts/update.sh`).
5. Проверить `/api/health` и версию в «Настройках».

### Риски и меры

| Риск | Мера |
|---|---|
| Сборка на слабом NAS (2 ГБ RAM) идёт долго или падает | Готовый образ из GHCR (B8) + `docker-compose.image.yml`; либо сборка на ПК и `docker save`/`load` |
| Container Manager не показывает прогресс сборки | В README — SSH-путь `sh scripts/update.sh` и `docker logs` |
| Удаление проекта с галочкой «удалить данные» уничтожает базу | Предупреждение в README + `scripts/backup.sh` в чек-листе |
| Zip теряет `+x`, CRLF ломает скрипты | Запуск через `sh`, принудительный LF в упаковщике, проверка `CR=0` |
| ARM-модели | Только готовый образ (B8), сборка на NAS не поддерживается |
| Секрет в `.env` внутри архива | Для публичных релизов `-NoEnv`; `.env` не коммитится, в README — предупреждение |

**Оценка:** 1,5–2 дня (каркас уже готов; осталось: прогон на NAS, CI-образ, GitHub Release).

## Открытые вопросы

1. **Автоправила (0.1):** нужно ли применять их к уже существующим операциям автоматически при создании правила или только по кнопке?
2. **OCR** — допустима ли отправка изображений во внешний сервис (Яндекс/Google) или требуется полностью локальное распознавание?
   → **Решено в 1.1.0:** только локальный `tesseract`; наружу изображения не уходят.
3. **Темы** — нужна ли синхронизация выбора между устройствами (серверное хранение) или достаточно `localStorage`?
   → **Решено в 1.1.0:** `localStorage`; серверная синхронизация — в бэклоге.
4. **Экспорт** — нужен ли режим обезличивания по умолчанию и есть ли ограничения на диапазон/объём?
   → **Открыто:** в 1.1.0 экспортируется весь профиль без параметров `from/to` и без `anonymize`.
5. **Импорт** — достаточно ли создавать одну операцию по чеку или нужна разбивка по товарам?
   → **Решено в 1.1.0:** одна операция по чеку; разбивка на позиции — в бэклоге.

> Решено: резерв пользователь настраивает сам (на счёте или общий), возврат из резерва контролируется только напоминаниями — без блокировок. Уведомления на этом этапе показываются всплывающим окном (toast) + блоком в «Обзоре».
