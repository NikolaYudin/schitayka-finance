## Принципы

1. **Данные пользователя неприкосновенны**: не использовать `EnsureDeleted()` в рабочем режиме, не трогать рабочие базы без явного запроса.
2. **Схема БД — через EF Core Migrations**; обратная совместимость со старыми базами.
3. **Приватность по умолчанию**: чувствительные данные не логируются и не отправляются наружу без необходимости.
4. **Каждая фича — API + UI + тесты + документация** (по возможности в рамках задачи).
5. **Секреты не хранятся в репозитории и релизных архивах**.

- **Автообновление:** релизная проверка/артефакты настроены (`app.zip` + `.sha256`), но есть дефект отображения прогресса (B21).

### 3. Вкладка «Обязательные платежи» — **реализовано 18.11.2026**

**Цель:** планировать и контролировать регулярные/обязательные платежи (не обязательно являющиеся долгом).

**Реализовано:**
- [x] Сущности `Obligation` и `ObligationPayment` (миграция `DebtsAndObligations`): название, получатель, категория, сумма, периодичность (разово / ежемесячно / ежеквартально / ежегодно / произвольно с интервалом в днях), дата следующего платежа, день платежа, счёт списания, напоминание, заметка, статус (активен / пауза / завершён), привязка к долгу (опц.).
- [x] Статус «просрочен» вычисляется по дате; день платежа сохраняется при сдвиге на следующий период (31-е число корректно переносится на последний день месяца).
- [x] Факты оплаты: сумма и дата, комментарий, необязательная операция по счёту (обычный расход с категорией платежа или категорией «Обязательные платежи»); дата следующего платежа сдвигается на один период от даты по графику, разовый платёж завершается.
- [x] Удаление факта оплаты удаляет связанную операцию и возвращает дату следующего платежа; удаление платежа удаляет всю историю и операции.
- [x] API: `GET /api/obligations?filter=active|paused|completed|all`, `summary`, `{id}`, CRUD, `POST {id}/pay`, `DELETE {id}/payments/{paymentId}`, `POST {id}/pause|resume|complete`.
- [x] UI: вкладка «Платежи» (`#/obligations`), сводка, фильтры, карточки, формы платежа и оплаты, история; виджет «Обязательные платежи» на дашборде с переключателем видимости (`sk_dashboard_widgets.obligations`).
- [x] Сам платёж в бюджет не входит — движение денег появляется только через созданную операцию (решение 18.11.2026); привязка к долгу и уменьшение остатка — Задача 4.

**Исходная структура (черновик):**
- Сущность `Obligation` (обязательный платёж): название, получатель, категория, сумма (фикс/ожидаемая), периодичность (`разово`, `ежемесячно`, `ежеквартально`, `ежегодно`, произвольно), дата следующего платежа, день платежа, счёт списания (опц.), напоминание (опц.), статус (`активен`, `пауза`, `завершён`), привязка к долгу (опц.).
- Факт оплаты: отметка выполнения/создание операции, перенос даты следующего платежа, просрочка.
- **Отображение на дашборде:** виджет «Обязательные платежи» с переключателем видимости (ближайшие платежи, сумма за период, просроченные).

### 4. Пересечение «Долги» и «Обязательные платежи» — **реализовано 18.11.2026**

**Принцип:** это разные сущности, которые могут быть связаны.

**Реализовано:**
- [x] Связь `Obligation.debtId` (nullable) хранится и редактируется в форме; в карточке платежа показывается название долга, в карточке долга — блок «Связанные платежи» с датой, суммой и статусом (только активные).
- [x] Оплата платежа, связанного с долгом «я должен», может по галочке создать событие `Repayment` и уменьшить остаток долга. Движение денег остаётся одним: операция создаётся только фактом оплаты, у события долга `TransactionId` не заполняется. Сумма больше остатка и погашенный долг отклоняются.
- [x] Удаление факта оплаты удаляет созданное событие возврата и восстанавливает остаток долга; удаление платежа — все его события. Событие, созданное оплатой, нельзя удалить отдельно из истории долга (нужно удалить факт оплаты).
- [x] При удалении долга связь обнуляется (`SetNull`), история долга удаляется, график платежей и факты оплаты сохраняются.
- [x] Виджеты «Долги» и «Обязательные платежи» включаются независимо; суммы планов и остатков не попадают в общую аналитику — в бюджете учитывается только созданная при оплате операция.
- [x] Миграция `ObligationDebtLinks` (ссылка на событие возврата в факте оплаты); всего 125/125 тестов.

- **Долг без обязательного платежа:** например, займ у коллеги без графика — создаётся только `Debt`, платежи фиксируются как события возврата.
- **Долг с обязательными платежами:** например, ипотека/кредит — `Debt` (остаток, условия) + связанный `Obligation`/график платежей (дата, сумма, напоминания). Оплата платежа может уменьшать остаток долга.
- **Обязательный платёж без долга:** коммунальные услуги, подписки, налоги — только `Obligation`.
- В UI/модели предусмотреть связь `Obligation.debtId` (nullable), отображение связанного долга в карточке платежа и предстоящих платежей в карточке долга.
- Дашборд-переключатели видимости настраиваются независимо для виджетов «Долги», «Обязательные платежи» (и календаря), но связанные элементы должны быть согласованы (без дублирования сумм в общей аналитике).

**Предлагаемая структура (черновик):**
- Источники событий: обязательные платежи, даты возврата/платежей по долгам, даты окончания вкладов, начисления/выплаты, пользовательские события/напоминания.
- Представления: месяц/неделя/список «ближайшие»; фильтры по типу события.
- Сущность пользовательского события (опц.): название, дата/время, тип, сумма (опц.), связь с долгом/платежом/счётом (опц.), напоминание.
- **Отображение на дашборде:** виджет «Ближайшие события» с переключателем видимости (N ближайших событий/платежей).

## Открытые вопросы

1. **Автоправила (0.1):** применять к существующим операциям автоматически при создании правила или только по кнопке?
2. **Экспорт:** нужны ли обезличивание по умолчанию, диапазон дат (`from/to`) и ограничения объёма?
3. **N2/B27 (решено):** канонический макет — гибрид: основа «светлое стекло» (вариант 2), жёлтый акцент и бейдж вклада (вариант 1), кольцо доходности (вариант 3).
4. **N3:** требуется ли отдельное продуктовое подтверждение текущей семантики семейных переводов?
5. **Инвестиции (котировки) — решено 18.11.2026:** основной источник — MOEX ISS (акции/ETF и облигации, без ключей), ручная цена — fallback; при недоступности источника цена не блокирует интерфейс. Расширение на другие рынки/провайдеры — при необходимости.
6. **Долги/обязательные платежи — решено 18.11.2026 и подтверждено реализацией 18.11.2026:** долги и сами обязательные платежи учитываются отдельно и не входят в доходы/расходы бюджета; операцию по счёту можно создать галочкой при возврате долга или оплате платежа — это единственный источник движения денег. Суммы долгов и плановых платежей не дублируются в аналитике, двойного учёта нет. Разница: созданная оплата обязательного платежа — это реальный расход с категорией, поэтому она (в отличие от возврата долга) участвует в бюджете и кэшбэке. Привязка платежа к долгу (`Obligation.DebtId`) реализована в Задаче 4: по галочке создаётся событие возврата и уменьшается остаток, но второе движение денег не создаётся (операция остаётся только у факта оплаты). Виджеты включаются независимо.

> Решения пересмотрены: OCR локальный по умолчанию, удалённый vision — по явной настройке; тема синхронизируется с сервером; импорт чека — одна операция или выбранные позиции.
